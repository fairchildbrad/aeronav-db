<objective>
## Goal
Make the weekly workflow build cycle N from the right previous file and refuse to build from a wrong one. The previous file is:
- the newest **schema-3 release older than N**, with its database checked against the sha256 in that release's manifest; or
- if no schema-3 release exists yet, the **seed pinned by sha256** in `identity/seed.json`.

## Purpose
sqwkd's Phase-2 note: "a wrong or tampered PREV can't silently re-mint or fork ids". A forced rebuild of N must chain from N-1, not from the latest release.

## Output
`aeronav_db/chain.py` (resolve, fetch and check the previous file), the workflow change, the seed pin file, tests, a local dry run, and a README note. **No push, no merge, no release, no seed upload.** All of these wait for the operator-confirmed first release after Phase 3.
</objective>

<acceptance_criteria>
## AC-1: Previous-file resolution
Given target cycle N and the repository's releases
Then `python -m aeronav_db.chain previous --cycle N --out DIR` writes DIR/previous.sqlite3 and prints its provenance. The source is:
- (a) the newest release tagged `cycle-D` with D < N whose manifest says schema_version 3. The database's sha256 must equal manifest.database.sha256 **and** the release's .sha256 asset; or
- (b) if no such release exists, the seed at identity/seed.json's `url`, whose sha256 must equal the pinned value and whose metadata cycle must equal the pinned cycle.
A forced rebuild of N therefore uses N-1, never N itself. A schema-2 release is never used as the previous file.

## AC-2: Refusals (exit non-zero, nothing written)
- sha256 mismatch against the manifest, the .sha256 asset or the pin;
- no schema-3 release and no seed pin;
- a download failure or short read;
- a gap: the previous cycle is not N-28 days. This is refused unless `--allow-gap` is passed (a workflow_dispatch input) and recorded in the build summary. The normal remedy is to dispatch the missing cycle first.

<!-- audit-added -->
## AC-6: Lineage is checked one hop back
Given a previous file P resolved by path (a)
Then P passes check_identity, and P's metadata previous_db_sha256 equals the database sha256 in the manifest of the release (or seed pin) named by P's previous_cycle. A swapped or hand-edited P, whose own release manifest was edited to match, still fails, because its parent hash does not chain.

## AC-3: Workflow
The build job runs `chain previous`, then `build --previous-db`, then `verify --previous`, then publishes. The release assets and notes carry `previous_cycle` and `previous_db_sha256`. The manifest gains `previous: {cycle, sha256}`. The release notes state the schema version and history_start. <!-- audit-added --> The first schema-3 release's notes and the README carry a migration notice: `airports.airport_id` is a new column; NASR 3-letter identifiers change code_type from 'iata' to 'faa'; consumers should check manifest.schema_version.
Before the step that publishes the first schema-3 release, a `seed_confirmed` guard requires identity/seed.json to have `"published": true`. The seed upload (a non-latest prerelease tagged `identity-seed-<cycle>`) is a manual, operator-confirmed step, documented in the README and not automated.

## AC-4: Seed pin and freshness
identity/seed.json = {cycle, sha256, url, reproduced_by}. Before the first release, the seed must end at N-1 of the first schema-3 cycle, so `backfill --to` is re-run then. A test asserts the pin matches dist/backfill/seed.sqlite3 when that file is present.

## AC-5: Local dry run
Run `chain previous` against the real repository releases with a `--seed-path` override for the unpublished seed. It falls back to the seed, because all releases are schema 2. Then build 2026-10-29 and verify --previous. Separately, simulate a schema-3 "release" directory to exercise path (a), including a forced rebuild of N picking N-1, and a tampered database being refused.
