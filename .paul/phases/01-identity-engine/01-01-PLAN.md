<objective>
## Goal
A pure-Python module `aeronav_db/identity.py`. Given the previous cycle's identity state (empty on the first run), the current cycle's effective date and the current cycle's source observations, it returns the next identity state. The function is deterministic and does no I/O.

## Purpose
cv-aviation's logbook needs a permanent airport id and dated code history (PROJECT.md decisions of 2026-11-06 and 2026-11-07). Keeping the engine pure lets Phase 2 replay years of archives through the same code path that the weekly build uses.

## Output
aeronav_db/identity.py and tests/test_identity.py. No change to build.py, the schema or verify (that is 01-02).
</objective>

<acceptance_criteria>
## AC-1: Ids are permanent, fixed-shape, never reused
Given any sequence of cycles
When identities are minted
Then every id matches ^AP\d{7}$, ids are allocated in ascending order from a persisted counter, and no id once issued is removed from the state (it stays an identity or becomes an alias source). Mint order within a cycle is sorted by (source, source_key), so the same inputs give the same ids.

## AC-2: Renames keep the identity (NASR)
Given NASR site 06278./A had ARPT_ID 2Y1 in cycle N-1 and has 47IA in cycle N
When cycle N is applied
Then the same airport_id holds the interval faa=2Y1 with valid_to=N, and a new interval faa=47IA with effective_date=N and valid_to=NULL.
Match order: (site_no, site_type) → site_no if unique in prior state → same FAA LID within 1 nm → mint. Each identity records its match_basis. This covers the 18AL site-number correction and the 40ND site-type change seen in real data.

## AC-3: OurAirports rows link to NASR identities inside US jurisdiction
Given an OurAirports row inside NASR_JURISDICTION that shares a code with a NASR observation within SAME_AIRPORT_NM
When the cycle is applied
Then it attaches to that NASR identity (ourairports_id is set, and its iata code becomes an iata interval on the same identity). Outside the jurisdiction, the OurAirports id is the matching key.
This fixes PBI/DJT: PBI and DJT both attach to one id, PBI is closed at the cycle where the source dropped it, and DJT opens at that cycle.

## AC-4: Absent ≠ closed
Given an identity seen in N-1 and missing in N
When N is applied
Then its presence interval is closed at N, its open code intervals are closed at N, and source_status is unchanged. Closure comes only from the source: NASR CI → closed_indefinitely, CP → closed_permanently, OurAirports type closed → closed. If the airport reappears later, it reuses the same id, with a new presence interval and new code intervals.

## AC-5: History is append-only and aliases are one hop
Given state N-1
When N is applied
Then every interval closed in N-1 is byte-identical in N, and only open intervals may close.
When two prior identities resolve to one current airport, the lower id survives, the higher becomes an alias (reason recorded), and any alias that pointed at the merged id is rewritten to point at the survivor. No alias target is itself an alias source.

## AC-6: Code lookup is answerable
Given the state
Then lookup(scheme, code, date) returns the airport_ids whose interval has effective_date ≤ date < valid_to (NULL counts as open), compared case-insensitively. It may return more than one id; IATA collisions are real and the caller disambiguates.
</acceptance_criteria>
