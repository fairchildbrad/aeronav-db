<objective>
## Goal
A field that both NASR and OurAirports list gets one airport_id. Today `_group` attaches an OurAirports row to a NASR record only through a shared IATA or ICAO code. A US field with an IATA code but no ICAO code (Jackpot 06U/KPT, Hyder SPB 4Z7/WHD) therefore gets two ids. The FAA LID that OurAirports carries in `local_code` becomes a pairing key inside the existing gate.

## Purpose
sqwkd ruling 2026-11-20: "ACCEPTED as a release blocker." Before release, the fix only changes which ids get minted. After release it would mean alias merges of published ids.

## Output
A pairing change, tests, a README line, a reconciled census, and a full seed re-run compared with e92fa5fe… and tz8. The results become the new baseline. No release.
</objective>

<rules_fixed_before_measurement>
These are decided now, before the numbers below are computed, so no threshold is chosen after seeing the data (sqwkd b, c, d, e).

- **R-a, key:** OA `local_code`, upper-cased and stripped, equals the FAA code that the NASR record carries **in the same cycle** (the code in that cycle's observation, not a historic interval). Both come from the same cycle's inputs, so a LID reassigned between cycles compares the current holder only (sqwkd e).
- **R-b, gate:** the existing `_can_pair` gate, unchanged: same country (or NASR jurisdiction or legacy successor), partner not already attached, distance ≤ SAME_AIRPORT_NM (25 nm). A local_code match is the same class of evidence as a shared IATA/ICAO code, so it goes through the same gate as those codes, and no new distance constant is introduced. The distance distribution is reported in full (AC-1 b). If it shows any local_code match between 1 and 25 nm that the per-pair review finds to be a different field, this rule comes back to sqwkd before APPLY continues. The threshold is not tuned.
- **R-c, gps_code:** gps_code is **not** a pairing key. In OA it is the GPS/ICAO-style identifier (e.g. "K06U"), not the FAA LID, and OA documents local_code as the national code. The census reports what a gps_code fallback would add, for information only.
- **R-d, one-to-one:** pair through local_code only when exactly one NASR record in the cycle carries that FAA code and exactly one OA observation carries that local_code. Otherwise don't pair, and list the case.
- **R-e, order:** a shared IATA/ICAO code is still tried first, and sticky attachment is unchanged. local_code is tried only when the row has no shared-code partner. It never overrides an existing shared-code pairing.

## Predicted before measurement (sqwkd a, g)
- **P1, forward:** current OA-only identities that pair under R-a..R-d. Predict 230–239. My 239 included the gps fallback; local_code alone gives slightly fewer.
- **P2, reverse:** current NASR identities with no OA attached whose cycle FAA code equals exactly one OA observation's local_code within the gate. Predict **equal to P1**. Under R-d both directions describe the same pair set, so any difference is a one-to-many case, and those get listed. Predicted one-to-many cases: 0–3.
- **P3, distance:** ≥ 95 % of P1 under 1 nm; 0–5 between 1 and 25 nm.
- **P4, gps fallback:** adds 0–5 beyond P1.
- **P5, the 10 = 249 − 239:** expected causes are no current NASR record with that LID, OA local_code empty or different (LID changed), or a non-airport kind. Each is explained by id.
- **P6, seed re-run:** ids no longer minted ≥ 239, up to ~300, because duplicates of fields closed before 2026-10 count too. airport_id_next drops by the same amount. New aliases: 0, because pairing happens before minting, so nothing merges. verify --previous exits 0 on every cycle of the chain. tz gate: present falls by roughly the current duplicate count (~27,226 − 239). NULL falls by most of that, because US OA-only duplicates have no county and sit in no_county_match. placed falls by the duplicates that were placed (non-US, and US placed through OA region rules).
